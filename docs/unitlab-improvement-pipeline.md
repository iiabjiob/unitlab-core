# UnitLab Pipeline (Demo-First, Raspberry Pi AP, C++ Periphery)

## Продуктовый контекст
- Raspberry Pi 5 = сервер + Wi-Fi точка доступа.
- Модули DI/DO/AO подключаются к этой AP автоматически.
- Инженер подключается к той же AP, открывает браузер и сразу работает.
- На этапе презентации: без сложной auth-модели, только пароль Wi-Fi.
- 2 глобальные сущности системы: `devices` и `channels`.
- 2 режима работы:
  1. Прямое управление железом.
  2. Работа через сигнал-лист (Excel) + аллокация каналов на сигналы.
- Основной workflow: one-click test run, где DO драйвит DI на SCADA-контроллере, а инженер визуально сравнивает ожидаемое vs фактическое.
- Дополнительно: режим выключателей/разъединителей/ножей.

## Цель этапа 1 (презентация)
Сделать «вставил SD-карту -> включил Pi -> открыл браузер -> запускай тесты» с фокусом на скорость проверки шкафов.

## Скорректированный pipeline

### 1. Zero-config запуск стенда на Raspberry Pi (обязательный)
Результат:
- Инженер не выполняет команды в терминале.
- После boot автоматически поднимается весь стек.

Что делаем:
- Преднастроенный образ (golden image): OS + Docker + Compose plugin + ваш стек.
- `systemd` сервис `unitlab.service` запускает `docker compose up -d` при старте.
- Автопроверка готовности: backend, ws, mqtt workers, redis, db, sequence/test-run worker.
- Единый env-профиль устройства (`/etc/unitlab/env`) без правки репозитория.

Критерий done:
- Новый Pi поднимает UI и backend автоматически за фиксированное время (например, < 90 сек).

---

### 2. Стабильный runtime для C++ периферии
Результат:
- DI/DO/AO модули стабильно общаются с платформой через MQTT/Wi-Fi.

Что делаем:
- C++ periphery-agent как отдельный контейнер (`periphery-agent`) с restart policy.
- Health endpoint/heartbeat для C++ агента, видимый в UI.
- Автовосстановление после пропадания Wi-Fi/перезапуска брокера.
- Фиксация версии протокола обмена (backend <-> C++ firmware/agent).

Критерий done:
- После рестарта Pi и повторного подключения модулей система автоматически восстанавливает связь.

---

### 3. Базовый режим «Прямое управление железом»
Результат:
- Инженер может управлять каналами и видеть обратные состояния/логи в реальном времени.

Что делаем:
- Надежный WS/MQTT event-flow без зависаний и потери команд в рамках demo нагрузки.
- Команды DO/AO + чтение DI/STATE.
- Понятный execution log: команда, ответ, статус канала, таймстемп.

Критерий done:
- Демо-сценарий с физическим шкафом проходит стабильно несколько раз подряд.

---

### 4. Signal List режим (ключевая ценность продукта)
Результат:
- Инженер импортирует Excel, делает аллокацию каналов и работает от «единого источника правды».

Что делаем:
- Импорт сигнал-листа из файла.
- Нормализация и валидация строк сигналов.
- Аллокация `signal -> channel` с сохранением и быстрым редактированием.
- В UI показываем одновременно:
  - ожидаемые сигналы из листа,
  - фактические события/состояния от железа/SCADA.

Критерий done:
- Можно загрузить реальный лист, привязать каналы и использовать в test run.

---

### 5. One-click Test Run для шкафов
Результат:
- Инженер запускает прогон набора сигналов в 1 клик и быстро сравнивает результат.

Что делаем:
- Сущность Test Run: набор сигналов + порядок/тайминги + запуск/останов.
- Исполнение последовательности DO воздействий.
- Лог прогона: шаг, ожидаемое состояние, фактическое состояние, итог.
- Визуальное сравнение 2 списков (expected vs observed).

Критерий done:
- Один прогон покрывает значимую часть шкафа за минуты.

---

### 6. Режим выключателей/разъединителей/ножей
Результат:
- Специализированные сценарии коммутационной аппаратуры доступны как отдельный режим.

Что делаем:
- Доменные шаблоны шагов/проверок для switchgear-объектов.
- Отдельный UI-поток и логика привязок каналов.

Критерий done:
- На демо можно показать как минимум 1 полноценный switchgear-сценарий.

---

### 7. Hardening после презентации
Результат:
- Переход от demo к промышленной эксплуатации.

Что делаем потом:
- Auth/AuthZ, MQTT ACL, секреты вне git.
- Надежность Redis Streams (reclaim зависших сообщений, DLQ, idempotency).
- Наблюдаемость, CI/CD, регрессионные тесты.

## Ближайший первый шаг (уже согласован)
**Добавляем Signal List из физического файла через Affino DataGrid.**

### Подшаги реализации
1. Backend endpoint для загрузки файла и парсинга Excel в нормализованный набор сигналов.
2. Модель/DTO сигнала + валидация обязательных колонок.
3. Frontend: загрузка файла и рендер таблицы в Affino DataGrid.
4. Editable grid: ручная правка значений и статусов валидации.
5. Сохранение импортированного набора как рабочей сущности для аллокации и test run.

### Definition of Done для шага 1
- Пользователь выбирает Excel-файл и видит строки в Affino DataGrid.
- Ошибки формата показываются построчно.
- Валидные строки можно сохранить как signal list dataset.
